# CAD-QA dataset regeneration — 1300 CadQuery programs (2026-10-19)

Date: 2026-10-19 · Status: completed, accepted for internal training and evaluation.
This is not a benchmark-release claim.

## Purpose

Regenerate the central CAD-QA task dataset with the current dataset-generation
code. The previous 10,000-row release was generated on 2026-06-20/21. The
dataset-generation code moved to `dataset/` on 2026-10-08 and `dataset/harbor.py`
changed on 2026-10-09, but no CAD-QA dataset row had been produced with that code.
This run closes the staleness gap recorded as LE-1.

## Inputs and provenance

- 1,000 CadQuery programs and their cached operation traces from
  `runs/current_cadevolve1000_10k_regen_20260613/sources.parquet` and
  `runs/current_cadevolve1000_cached/trace/traces.parquet`.
- 300 top-up CadQuery programs from
  `runs/current_cadevolve1000_10k_regen_20260613_topup300/sources.parquet`,
  freshly traced for this run.
- The cached operation traces cover exactly the 1,000 CadQuery program IDs used
  here. The code that produces CadQuery program operation traces has not changed
  since the cached traces were written, so those operation traces were reused
  rather than re-executed.
- Combined: 1,300 CadQuery programs and 1,300 operation traces.

## Environment

- Local workstation, 8 CPU cores, 14 GiB RAM, CPU-only.
- The host reset twice during the run. The generation work was sharded and
  resumable; completed shards were validated before reuse.
- Large CAD ontology graph shards were split into 25-graph subshards to bound
  memory. No GPU was used.

## Commands

```bash
cadqa trace run \
  --sources-jsonl runs/current_cadevolve1000_10k_regen_20260613_topup300/sources.parquet \
  --out runs/regen_1300_traced_20261019/traces_topup \
  --timeout-seconds 30 --workers 8

cadqa graph build \
  --sources-jsonl runs/regen_1300_traced_20261019/sources.parquet \
  --traces-jsonl runs/regen_1300_traced_20261019/traces_combined.parquet \
  --out runs/regen_1300_traced_20261019/graph --shard-size 100

cadqa query synthesize \
  --graph runs/regen_1300_traced_20261019/graph/graphs/part-00000.parquet \
  --out runs/regen_1300_traced_20261019/query_shards/part-00000 \
  --max-per-family 5

cadqa dataset materialize \
  --queries runs/regen_1300_traced_20261019/query_shards/part-00000/queries.parquet \
  --graphs runs/regen_1300_traced_20261019/graph/graphs/part-00000.parquet \
  --out runs/regen_1300_traced_20261019/dataset_shards/part-00000

cadqa dataset export-release \
  runs/regen_1300_traced_20261019/dataset_stream_bounded \
  --out runs/regen_1300_traced_20261019/release_10k \
  --release-tier benchmark-release --allow-failing-release-gates

cadqa training export-sft \
  --rows runs/regen_1300_traced_20261019/release_10k/rows.parquet \
  --out runs/regen_1300_traced_20261019/release_10k/sft \
  --release-tier benchmark-release --allow-failing-training-gates
```

The query-synthesis and materialization commands ran once per CAD ontology graph
shard or subshard. The full command sequence and log are in
`runs/regen_1300_traced_20261019/run.sh`, `finish_shards.sh`,
`run_split_shards.sh`, and `logs/driver.log`.

## Generated pool

- 1,300 CAD ontology graphs, 13 graph shards of 100 graphs.
- 218,779 CAD-QA dataset rows in 28 row shards.
- 59 release families present in the full pool.

## Bounded candidate pool

The first release export over all 218,779 CAD-QA dataset rows reached 12.3 GiB
RSS and was stopped before the host could run out of memory again. The export
therefore ran from a bounded candidate pool:

- 78,988 CAD-QA dataset rows, 16 row shards.
- At most 1,500 rows per prompt family.
- At most 15 rows per CAD model per prompt family.

The bound is a memory control, not a quality filter. It keeps every release
family and samples multiple CAD models per family, but it is not the full
generated pool.

## Benchmark-release status

The release is not `valid_for_release` at the `benchmark-release` tier. The
blocking gates are:

| Blocking gate | Result | Requirement |
|---|---|---|
| `distinct_cad_model_coverage` | 980 CAD models | 1,000 |
| `prompt_family_balance` | largest prompt family 10.43% | at most 10% |
| `answer_entropy` | 7.50 bits | 8.0 bits |
| `cross_feature_value_bearing_coverage` | 488 rows | 500 rows |
| `intended_family_coverage` | 42 release families | 59 |
| `parameter_balance` | 112 violations | 0 |

### Root causes

- 15 of the 17 missing release families fail release validation uniformly with
  `missing_clue_clause_map`. They are the face, kernel-face, CadQuery selector-count, and
  face-spatial-relation families. The bounded pool contains release-ready
  candidates for all of them, but validation rejects every candidate.
- `parameterized_void_region_volume` fails `geometry_first_prompt_policy` on all
  candidates.
- `answer_entropy` is structurally capped at 7.91 bits by the current
  answer-format mix; the largest component, candidate-label answers, has only
  seven possible public labels.
- Distinct CAD model coverage is 20 short. Release balance capping drops the
  remaining CAD model representatives even though the bounded pool spans more
  CAD models.

The answer-format history — which formats were cut, when, and why — is recorded
in `../_archive/dataset-pre-rebuild-2026-10-21/answer-formats.md`.

## Decision

Accepted as the current regenerated CAD-QA dataset for internal SFT and
evaluation experiments. Do not use this release for a benchmark claim until the
blocking gates above pass.

Follow-ups:

1. Fix `missing_clue_clause_map` for the 15 affected families and re-export.
2. Decide whether `parameterized_void_region_volume` should be a release family
   or a review-only family.
3. Decide the answer-entropy policy: change the answer-format mix or document
   why 8.0 bits is not achievable at the required row count.
4. Improve CAD model coverage and parameter balance in release selection.
