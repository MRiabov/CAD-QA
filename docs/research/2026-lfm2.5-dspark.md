# LFM2.5-DSpark — draft speculators for speculative decoding (2026)

**Status:** external study note (Liquid AI blog + vLLM docs), 2026-10-09. Records whether LFM2.5 has an
MTP/draft component and how fine-tuning relates to it.

## Citation

- Liquid AI, "LFM2.5-DSpark: Up to 3.2x Faster Inference from H100 to MacBook", Liquid AI blog, Aug 2026.
  `liquid.ai/blog/lfm2.5-dspark`. `[vendor]`.
- vLLM, "MTP (Multi-Token Prediction)", vLLM docs, 2026.
  `docs.vllm.ai/.../features/speculative_decoding/mtp`. `[vendor]`.

## Method

DSpark is a speculative-decoding draft speculator that combines a DFlash-style parallel backbone conditioned
on the target's context features, a lightweight Markov sequential head (adds dependency between drafted
tokens), and a confidence-scheduled acceptance head that prunes low-confidence suffixes.

## Finding

- LFM2.5 is **next-token-prediction**; it has **no built-in MTP head**. Liquid ships **DSpark** as a
  *separate* ~300M draft checkpoint (`LiquidAI/LFM2.5-{1.2B-Instruct,2.6B,8B-A1B}-DSpark`; safetensors +
  GGUF), with day-one support in **llama.cpp** and **SGLang** — not vLLM.
- Under greedy decoding the emitted sequence is **identical** to the target by construction, so benchmark
  accuracy (pass@1 / exact match) is unchanged; speedup is up to ~3.2x on GPU, ~2.9x on device.
- vLLM's `method: mtp` path serves models with **native** MTP (Gemma 4 assistant, MiMo, Qwen3-Next);
  LFM2.5 is not on that list, so MTP speculation does not apply to it.

## Why it matters for CAD-QA

- We do **not** train or update a draft/MTP head: `liquid-finetune` / LEAP (a TRL wrapper for
  SFT/DPO/GRPO + `evals:` + GGUF export) has no speculator path, and the shipped draft targets the
  **base** LLM model, so its acceptance degrades after our LoRA SFT + merge.
- Speculation is **lossless**, so it is a serving throughput knob only — never an accuracy or training
  decision. Adopting it would move the serving runtime from vLLM to SGLang (FT-D22).
