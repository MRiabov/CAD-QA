# CAD-QA Epics and Stories

This document is the human-readable planning view for CAD-QA. The machine-readable
status source is [`epics-and-stories.yaml`](epics-and-stories.yaml), but this file
adds two review fields for each epic and story:

- **Acceptance criteria**: the user-visible value that must be true.
- **Technical definition of done**: the concrete implementation, verification,
  and artifact evidence required before the item should be marked implemented.

## Current Direction

CAD-QA is one graph-first benchmark system:

```text
source records
-> optional trace/snapshot evidence
-> typed CAD ontology graph
-> deterministic query programs
-> verifier-backed candidate traces
-> rule-rendered prompts
-> public/private dataset rows
-> release/SFT validation gates
```

Main benchmark and default SFT rows must require geometry-derived evidence, not
source-code syntax lookup. The training-critical surface is kernel/geometry-backed
CAD reasoning: volumes, bounding boxes, centroids, topology deltas, selector-result
geometry, material/void deltas, path distances, stable spatial relations, and
value-bearing multi-hop prompts.

Recent policy updates:

- Generated release task families must each account for **1%-10%** of release/SFT
  rows or release is blocked.
- Intended release families that generate zero rows must become machine-visible
  through an intended-family manifest and block release unless moved to
  review-only/calibration status.
- Task families must be maximally parameterized. Axes, view words, min/max
  direction, exact values, comparison relations, target/reference entity types,
  subtype choices, narrowing predicates, and final selectors should be sampled
  row parameters whenever the verifier can support them.
- Sparse direct extrema are not dead task families. They should be generated by
  graph-hop query synthesis: intended family specs, reusable geometry-derived
  narrowing predicates, bounded clause-chain search, sampled final selectors, and
  normal resolver/verifier/rendering.

The `benchmark-release` level is the canonical public benchmark and real
fine-tuning bar. Smoke and release-candidate tiers are development gates; they
can demonstrate mechanics, but they cannot support benchmark-release claims.
Dataset cards, paper tables, SFT manifests, and experiment summaries may use
benchmark-ready or fine-tuning-ready language only when the artifact passes the
`benchmark-release` profile. Smoke and release-candidate labels are not weaker
benchmark-release levels and cannot be promoted by prose.
The executable profile, this planning document, and `specs/dataset-spec.md`
must stay synchronized; changing a threshold or blocking dimension requires
updating all three plus the machine-readable `release_tiers` block in
`epics-and-stories.yaml` and the profile/spec consistency tests:
`epics-and-stories.yaml` also records `canonical_release_tier:
benchmark-release` so the target release level is explicit metadata, not only
prose.

| Gate | Benchmark-release requirement |
| --- | --- |
| Release rows | At least 10,000 public/private release rows. |
| Default SFT rows | At least 10,000 rows after default geometry-critical filtering. |
| Generated task-family count/share | At least 10 generated release families; every generated release family is between 1% and 10%. |
| Zero-row intended families | 0 intended release families with zero rows unless `review_only` or `calibration`. |
| Default SFT geometry-critical share | At least 99%. |
| Default SFT syntax-only calibration share | 0%. |
| Benchmark syntax-only calibration share | At most 2%, or separate calibration artifact. |
| Geometry-hop-positive share | At least 95%. |
| Main BrowseComp hop share | At least 90% with `logical_hop_count >= 3`. |
| Value-bearing measurement share | 15%-30%. |
| Cross-feature value-bearing share | 5%-15%. |
| Candidate breadth | Minimum 2 candidates before the final selector; median pre-final breadth at least 4. |
| Prompt-template count/share | At least 20 prompt templates; at most 5% per template. |
| Unique answer count | At least 1,000. |
| Answer entropy | At least 8 bits. |
| Parameter value max share | At most 35% within each parameterized family unless geometry-limited. |
| Axis/direction coverage | Each supported sampled value at least 20% unless geometry-limited. |
| Split quality | Train/validation/test splits, at least 3 protected groups per split, no train-only collapse. |
| Manual preview | At least 20 sampled rows per changed release family, or all rows if fewer exist. |
| New-family tests | Positive generation, failure/quarantine, and release-report accounting coverage. |

A benchmark-release artifact is ready only when the benchmark-release verifier
reports `valid_for_release=true`, has no blocking gates, and the default SFT
export passes the same tier. Any missing intended family, collapsed sampled
parameter, stale preview, absent test evidence, weak split, or failed numeric
threshold keeps the artifact in development status.

## Status Meaning

- `planned`: required or desirable work is defined, but implementation evidence is
  absent or insufficient.
- `work-in-progress`: core pieces exist, but coverage, distribution, release gates,
  or manual review are not sufficient to call it done.
- `implemented`: the mechanism exists, has tests or reviewed artifacts, and passes
  the relevant current checks. This does not imply every future family or release
  distribution is complete.

## Epic 1: Project framing and graph-first spec (`epic-1`)

Status: `implemented`
Priority: `P0`

Acceptance criteria:

- Users can understand CAD-QA as one graph-first benchmark rather than a loose
  collection of task scripts.
- Low-hop calibration rows and high-hop BrowseComp-style rows are clearly framed
  as slices of the same ontology/query/verifier pipeline.

Technical definition of done:

- Core specs and README describe the graph-first architecture, row types, hidden
  verifier artifacts, and paper narrative.
- Legacy split task-family framing is marked obsolete.

| Story | Status | Acceptance criteria | Technical definition of done |
| --- | --- | --- | --- |
| 1.1 Replace split task-family framing with one ontology-query system | `implemented` | Users see one coherent system for all CAD-QA rows. | Specs define the source -> graph -> query -> verifier -> row path and remove separate generator framing. |
| 1.2 Define low-hop and high-hop rows as hop-count slices | `implemented` | Users can separate calibration rows from benchmark rows by evidence and hop count. | Dataset/task specs define logical/static/geometry hops and how they are reported. |
| 1.3 Paper narrative: CAD-QA as BrowseComp for CAD | `implemented` | External readers understand the benchmark thesis and why geometry-backed uncertainty matters. | Paper-facing docs describe CAD-QA as BrowseComp-style CAD reasoning with candidate traces and deterministic grading. |

## Epic 15: Benchmark-release numeric readiness tier (`epic-15`)

Status: `implemented`
Priority: `P0`

Acceptance criteria:

- Benchmark-release artifacts contain at least 10,000 release rows and at least
  10,000 default SFT rows.
- Default SFT rows are at least 99% geometry-critical and 0% syntax-only
  calibration.
- Benchmark rows are at least 95% geometry-hop-positive and at least 90%
  `logical_hop_count >= 3`.
- Value-bearing measurement rows are 15%-30% and cross-feature value-bearing rows
  are 5%-15% of benchmark-release rows.
- Prompt templates are capped at 5%, answer entropy is at least 8 bits, and at
  least 20 prompt templates and 1,000 unique gold answers are present.
- High-hop rows have at least 2 pre-final candidates and median pre-final
  candidate breadth of at least 4.
- Parameterized families keep sampled values at or below 35% share and supported
  axis/direction values at or above 20%, unless geometry-limited.
- Multi-split benchmark releases have train/validation/test splits, at least 3
  protected groups per split, and no train-only collapse.

Technical definition of done:

- Release verifier, SFT exporter, dataset reports, preview tooling, and
  readiness docs support explicit release-tier profiles. The benchmark-release
  profile enforces the numeric gates above and marks artifacts failing them as
  not benchmark-release ready.

## Manual Review Requirements Before Marking Implemented

For any story that adds or changes task generation:

1. Generate a Markdown preview with actual sampled prompts, source code, hidden
   query programs, candidate traces, and gold answers.
2. Confirm prompts use conventional CAD/mechanical-engineering terminology rather
   than implementation-detail wording.
3. Confirm public clues cannot be solved from source syntax alone unless the row is
   explicitly calibration.
4. Confirm candidate traces preserve distractors until the intended resolving hop.
5. Confirm release/SFT reports pass active gates, including geometry-critical
   dominance, value-bearing coverage where applicable, 1%-10% generated-family
   balance, and parameter coverage once implemented.
6. Be conservative: if scale, balance, or review evidence is missing, leave the
   story `work-in-progress` or `planned`.
