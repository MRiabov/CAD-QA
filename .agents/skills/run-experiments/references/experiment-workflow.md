# CAD-QA Experiment Workflow

Use this reference for CAD-QA and CADEditQA dataset, orchestration, SFT,
Vast.ai, monitoring, and artifact-preservation tasks. Keep dated observations
and outcomes in `docs/experiments/`; keep reusable operational procedure here.

## Local Preflight

Run only the checks relevant to the code touched, but do not rent GPU before
basic local validation is clean.

```bash
rtk uv run python -m compileall -q cad_qa scripts tests
rtk uv run pytest -q
rtk uv run python -m scripts.experiments.run_experiment_suite configs/orchestration_smoke.yaml --list
rtk uv run python -m scripts.experiments.run_experiment_suite configs/orchestration_smoke.yaml --dry-run
rtk uv run python -m scripts.experiments.run_experiment_suite configs/overnight_experiment_suite.yaml --run answer_sft_canary --with-dependencies --dry-run
```

The wrapper script runs the same common local gates:

```bash
rtk scripts/experiments/run_cadqa_experiment.sh preflight
```

For trace-backed dataset changes, also run CadQuery-enabled generation and
validation on a small CADEvolve probe:

```bash
rtk uv run --extra cadquery cadqa generate --auto-source-dir \
  --output-dir runs/cadevolve_trace_probe/dataset \
  --limit 3 \
  --workers 1 \
  --trace-timeout-seconds 30
rtk uv run --extra cadquery cadqa validate runs/cadevolve_trace_probe/dataset
```

For SFT data changes, prepare and smoke the chat JSONL before optimizer updates:

```bash
rtk uv run python -m scripts.training.prepare_answer_sft_dataset \
  --dataset-dir runs/cadevolve_trace_probe/dataset \
  --output-dir runs/cadevolve_trace_probe/sft \
  --max-train-rows 512 \
  --max-eval-rows 128
rtk uv run python -m scripts.training.text_sft_smoke \
  --sft-dir runs/cadevolve_trace_probe/sft
```

## Dataset And Split Rules

- The cheap default dataset is generated by `cadqa smoke`.
- Larger code-plus-label datasets should be generated with
  `cadqa generate --auto-source-dir` or an explicit CADEvolve source directory.
- The most recent local note found a 30 second trace timeout safer than 10
  seconds for adjacent CADEvolve probes.
- Validate every generated dataset with `cadqa validate` or
  `scripts.dataset.dataset_stats` before training.
- Optimizer updates may use public `train` rows only.
- Validation, `test_*`, held-out source, counterfactual, and CADEditQA groups
  are evaluation-only unless a manifest explicitly creates an internal
  group-safe split from public `train`.
- Do not split counterfactual or edit-counterfactual groups across internal
  train/eval.

Useful dataset commands:

```bash
rtk uv run cadqa smoke --output-dir runs/smoke_dataset/dataset
rtk uv run cadqa validate runs/smoke_dataset/dataset
rtk uv run python -m scripts.dataset.dataset_stats \
  runs/smoke_dataset/dataset \
  --output runs/validate_smoke_dataset/dataset_stats.json
rtk uv run python -m scripts.dataset.balance_dataset_classes \
  runs/smoke_dataset/dataset \
  --output-dir runs/cadqa_balanced \
  --max-rows-per-task 200
```

## Manifest Execution

Prefer the manifest runner so runs are dependency-checked, restartable, and
artifact-indexed.

Useful controls:

- `--list` shows available runs.
- `--dry-run` prints the selected plan without executing it.
- `--run NAME` selects one run; repeat for multiple runs.
- `--with-dependencies` expands selected runs to their transitive dependencies.
- `--skip-dependencies` is for manual recovery only.
- `--resume` skips already completed runs with `run_status.json`.
- `--runs-dir PATH` changes the default run directory when a manifest entry does
  not provide `output_dir`.

Examples:

```bash
rtk uv run python -m scripts.experiments.run_experiment_suite \
  configs/orchestration_smoke.yaml --resume

rtk uv run python -m scripts.experiments.run_experiment_suite \
  configs/overnight_experiment_suite.yaml --run answer_sft_canary --with-dependencies --dry-run
```

The convenience wrapper covers the common cases:

```bash
rtk scripts/experiments/run_cadqa_experiment.sh list
rtk scripts/experiments/run_cadqa_experiment.sh smoke
rtk scripts/experiments/run_cadqa_experiment.sh canary-dry-run
```

## Vast.ai Instance Selection

For meaningful Qwen3.5 4B answer-SFT runs, use A100 80GB-class or H100-class
capacity. Small 16GB cards are only for environment smoke tests.

Selection policy:

1. Filter offers first: one GPU, GPU RAM near 80GB for A100/H100-class runs,
   enough disk, direct SSH ports, CUDA-compatible PyTorch image, and acceptable
   reliability.
2. Sort the filtered offers by `dph_total` or equivalent total hourly price
   ascending, not by raw GPU type or list order.
3. Prefer spot only when it is actually available near budget; otherwise use the
   cheapest matching on-demand offer.
4. After creation, immediately verify live GPU name, VRAM, disk, CUDA state, and
   total hourly price. Destroy and recreate before bootstrapping if the live
   instance does not match the requested budget or hardware class.
5. Destroy failed, overpriced, or finished contracts after artifact upload is
   verified.

Typical teardown:

```bash
printf 'y\n' | rtk uv run vastai destroy instance <contract_id>
```

Keep SSH keys, tokens, account balance, and live credentials out of repo files.

## Vast Bootstrap

Use the PyTorch image's existing CUDA Python. Do not create a second virtualenv
unless the image is known broken. Get the repository onto the instance using
the authenticated clone/pull method appropriate for the project, then bootstrap
from the checkout:

```bash
cd /root/CAD-QA
bash scripts/devops/bootstrap_vast_instance.sh
```

The bootstrap script installs `uv`, installs the project with
`CADQA_EXTRAS=dev,cadquery,training` by default, and prints Python/Torch/CUDA/GPU
state. Override `CADQA_EXTRAS` only when a smaller environment is intentional.

Confirm CUDA after bootstrap:

```bash
cd /root/CAD-QA
python - <<'PY'
import torch
print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))
PY
```

## Launch And Monitor

Run long jobs in `tmux` or `nohup`:

```bash
tmux new -d -s cadqa-sft \
  'cd /root/CAD-QA && python -m scripts.experiments.run_experiment_suite configs/overnight_experiment_suite.yaml --run answer_sft_canary --with-dependencies > overnight.log 2>&1'
```

Monitor:

```bash
tail -n 160 overnight.log
nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv,noheader
df -h /root
python -m scripts.experiments.monitor_experiment_run runs
```

Watch the first optimizer steps and first quality/eval artifacts for every new
recipe. Track loss, exact quality, invalid-output rate, completion length,
truncation, GPU utilization, disk, checkpoint writes, and expected artifacts.

Treat steady-state GPU compute or memory utilization below 75% as
underutilization; the target is 90%+ when the model, batch shape, generation
path, and memory budget allow it. Do not let an expensive run continue for hours
with low utilization unless there is a deliberate bottleneck being measured.

When utilization is low, tune the config before continuing. Candidate knobs:

- increase per-device train batch size until close to the VRAM limit;
- adjust gradient accumulation to preserve effective batch size;
- reduce overly frequent generation-heavy eval callbacks;
- use a single evaluation path per budget run;
- shorten prompts/completions only if token length, not batching, is the
  bottleneck.

If the run has not progressed far past the latest checkpoint, stop it, change
the config, and resume from that checkpoint. If discarding post-checkpoint work
would be material, wait until the next checkpoint is written, then stop and
resume from that checkpoint. Record the observation, changed knobs, and resume
checkpoint in the experiment record.

## Experiment Records

Persist every meaningful experiment, or coherent set of closely related
experiments, in a dated file under `docs/experiments/`. Do this for failed
canaries, negative results, interrupted runs, dataset/report-only runs, and
successful training runs. The record is the durable research log; performance
tuning is only one secondary part of it.

Each experiment record should include:

- purpose, hypothesis, and decision being tested;
- dataset source, dataset path or revision, split names, internal split method,
  row caps, and leakage/balance status;
- model, adapter initialization, prompt mode, decoding mode, reward components,
  and feature-exposure mode;
- exact command or manifest entry, plus any config diff from the previous run;
- hardware, Vast contract class when applicable, runtime stack, disk size, and
  approximate cost;
- checkpoints used for resume and best-checkpoint selection rule;
- monitoring notes, including GPU compute/memory utilization, step time, OOMs,
  disk pressure, invalid-output rate, and stop-rule triggers;
- metrics and qualitative outcomes by split/task where available;
- failures and negative findings, including what not to repeat;
- artifact paths, upload locations, checksums, and local mirrors;
- follow-up decision: stop, rerun with changed config, promote config to
  manifest default, or run the next gate.

## SFT Defaults

Default model for current budget runs: `unsloth/Qwen3.5-4B`.

Answer-only SFT:

- Use public prompt and canonical structured answer pairs only.
- Keep optimizer rows restricted to `train`.
- Run `scripts.training.text_sft_smoke` before GPU training.
- Use the manifest `answer_sft_canary` before promoting to a longer run.
- Preserve `train_result.json`, logs, adapter/checkpoint outputs, and eval
  metrics before teardown.

Reasoning SFT:

- Use generated rationales only when they can be grounded in trace metadata.
- Generate datasets with `scripts.training.prepare_reasoning_sft_dataset`.
- Keep public canonical `answer` unchanged and put rationale text in supervised
  completion fields.
- Validate generation quality before any longer run.

## Bounded Verifier Experiments

This repo currently exposes parser/verifier-backed rejection-sampling candidate
scoring. Use it as the first bounded verifier experiment before adding RL
manifests:

```bash
rtk uv run python -m scripts.training.score_rejection_sampling_candidates \
  --rows runs/smoke_dataset/dataset/jsonl/validation.jsonl \
  --candidates runs/model_candidates.jsonl \
  --output-dir runs/rejection_sampling_rewards \
  --max-candidates-per-row 16
```

Do not add a long RL job until SFT canaries are healthy, invalid-output rate is
controlled, verifier rewards are non-degenerate, and held-out quality is not
obviously regressing.

## Stop Rules

Hard stop:

- dataset validation or leakage audit fails;
- SFT JSONL format smoke fails;
- training loss becomes NaN;
- repeated OOM after reducing batch/completion settings;
- disk is close to full;
- expected artifacts cannot be written;
- live Vast price exceeds budget;
- run exceeds budget.

Soft stop or pause:

- invalid-output rate remains high after prompt fixes;
- reward improves while held-out exact quality falls;
- all gains concentrate in one easy task;
- CADEditQA exact accuracy stays at zero after targeted canaries;
- completions collapse to common labels such as `no`, `0`, or `disjoint`;
- reasoning length is filler or repetition.

## Artifact Contract

Every expensive run should preserve:

- `run_status.json`
- stdout/stderr logs
- manifest/config used for the run
- exact command
- environment and git state
- dataset metadata and split manifest hashes
- metrics JSON/JSONL
- predictions or graded outputs when evaluation is involved
- checkpoints or adapters when training is involved
- artifact manifest with checksums
- upload or staging path

Before destroying a rented instance:

1. Compress run artifacts or use the manifest upload target.
2. Upload adapters, checkpoints, logs, metrics, predictions, and tarball
   checksums to the configured durable location.
3. Verify the uploaded artifact list or local mirror.
4. Record artifact URLs, paths, checksums, live hardware, runtime stack,
   command, and outcome in the dated experiment file.
5. Destroy the Vast instance.

If upload fails, preserve a local tarball plus checksum and record the failed or
deferred upload command.

## Known Failure Modes

- Small disks fill quickly once model caches, checkpoints, and tarballs coexist.
- Generic CUDA/PyTorch images can have incompatible Transformers, TRL, or
  Unsloth combinations; record the runtime stack before training.
- Plain SFT without assistant-only masking can overtrain on prompt
  reconstruction when the trainer path changes.
- Random row caps can starve rare CAD-QA or CADEditQA families. Use
  task-balanced caps for canaries when possible.
- Internal trainer eval plus a separate quality callback can duplicate
  expensive generation. Pick one evaluation path per budget run.
